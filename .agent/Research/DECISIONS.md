# ADR｜私人助理：我们为什么这样设计

整理日期：2026-10-30。

这是一篇关于项目选择的完整记录：为什么从日记模板走到 AI 助理，为什么采用现在的技术组合，哪些办法试着讨论过却没有留下，以及真实使用中的问题怎样改变了设计。

这篇文章解释理由。具体接口和开发步骤见 [ARCHITECTURE.md](ARCHITECTURE.md)。文中的“决定采用”表示设计选择，不等于已经开发完成。

## 一、最初要解决的，其实不是“缺一个机器人”

### 1. 从日记到助理：记录了，不等于事情会继续

项目最早的目标很朴素：把一个已有的 Obsidian 仓库整理成可以直接开始使用的日记模板。用户不需要其中大部分科研功能，只想保留日常记录，以及年、季、月、周、日之间的联系。

后来问题变了。日记能保存今天发生了什么，计划能写出明天应该做什么，但它们不会自己来找用户。如果一件事没有开始，或者做到一半遇到困难，笔记仍然安静地躺在那里。每一次重新想起、判断和安排，最后还是落回用户身上。

因此，这个项目逐渐从“保存记录”走向“有人接住交代”。所谓助理，是用户交代以后，不必把这件事一直挂在脑子里：该查的材料能查，该到点提示的会提示；发生变化以后，下一步仍然有人处理。

可以有三条路：

| 做法 | 用户得到什么 | 还留给用户什么 |
| --- | --- | --- |
| 只改进日记模板 | 更容易记录、回看、整理 | 何时开始、遇到变化怎么办，仍需自己想起 |
| 增加固定提醒 | 到点有人发消息 | 提醒之后如何行动、如何处理困难，仍需自己判断 |
| 做持续协作的助理 | 把提醒、资料、安排和反馈接起来 | 用户保留重要选择，系统承担已授权的后续工作 |

我们选择第三条。原因不在于它听起来更智能，而在于用户真正想减少的，是反复记事和重新决策的负担。如果只是把日历换成一个会说话的闹钟，并没有解决这个问题。

这也给范围画了一条线：助理需要负责推进，不能替用户假装已经行动。它可以打开材料、整理下一步，不能把这些准备记成用户已经背完单词。

### 2. 极简不是功能少，而是不要让用户替系统做事

用户反复表达的产品观是：来了就用，用完就走。这个要求影响的不只是页面好不好看，还影响整个系统怎样分工。

例如，助理明明能读到上一次的安排，却还要求用户重新说一遍；明明已经接受了四件事，却要求再确认四次；明明是系统模板字段的问题，却让用户解释字段怎样计算。这些操作单独看都很小，累积起来却让“私人助理”变成了另一个需要照顾的工具。

极简有两种很不同的做法。

一种是让程序尽量简单，把不确定的地方都交给用户：用户自己建日记、自己同步文件、自己逐项确认。开发工作少了，但使用工作多了。

另一种是内部把来源、状态和责任分清，让用户只处理必要的决定。这种做法对工程要求更高，但更符合本项目的目的。

我们选择后一种。不过这不意味着无限增加后台功能。只有当内部机制确实能减少用户操作、避免错误或保证接续时，才值得加入。否则，复杂度只是从界面背后长出来，并没有产生价值。

后面所有技术取舍，都要回答同一个问题：这个东西是在替用户承担负担，还是在制造一种新的维护负担？

### 3. 为什么要先减少评分、说明和重复汇总

最初的模板里有比较多的项目、评分和说明。用户直接指出，主观打分太累，每次新建笔记还要删说明也很麻烦。我们没有把这理解为“不愿意认真记录”，而是把记录本身的成本当作设计问题。

| 模板方式 | 长处 | 对这个用户的主要问题 |
| --- | --- | --- |
| 全面日课、评分和多项复盘 | 信息完整，方便统计 | 每天都要做很多额外判断，容易形成负担 |
| 完全空白 | 自由，没有填表压力 | 缺少用户希望保留的反思提示 |
| 少量清楚的标题 | 有提醒，也允许自由写 | 数据不完整，不能期待所有内容都量化 |

最终保留少量标题，去掉每日评分，把使用解释放到正文外面。这里主动放弃了“每一天都有漂亮的数据”的目标。

年、季、月、周、日也采用类似判断。我们需要它们逐层推进，但不需要每一层再抄一遍下一层。周记应该帮助回答“上周试的做法有没有用，下周怎么继续”，而不是机械汇总七篇日记。

这个决定的依据主要是用户明确反馈和实际用途，而不是已经做过长期对照实验。福格行为模型提醒我们关注行为难度和提示，但不能据此宣称“取消评分一定让所有人坚持”。

### 4. 为什么习惯和任务不能合成一个“完成”按钮

用户很早就区分了两件事：习惯关注有没有做，任务关注有没有达到具体结果。后来又出现第三件事：助理自己答应查资料、调整安排或等待反馈，也需要记住。

如果三者共用一个“完成”状态，就会出问题。

例如，打开词表读一个词，可能已经满足约定的习惯最低动作；但“掌握一百个词”的任务显然还没完成。助理把词表找到了，也不能算用户已经学过。

| 设计 | 好处 | 会出现的混淆 |
| --- | --- | --- |
| 全部放进一张待办表 | 简单 | 行为发生、成果达标和助理办事混在一起 |
| 分成三套独立软件 | 各自清楚 | 用户要维护多套系统，信息需要反复同步 |
| 同一体系里区分三类责任 | 关联方便，事实清楚 | 程序需要分别定义完成条件 |

我们采用第三种：习惯记录最低行为，任务保存验收标准，助理的后续责任单独表示。它们相互引用，但不替代彼此。

这里还有一个容易忽略的原则：降低启动难度，不等于悄悄降低最终目标。助理可以建议先学五分钟，但不能因此把原来需要交付的成果改成“碰过就算完成”。目标是否要调整，需要明确决定。

## 二、先确定什么归自己，再选择用什么技术

### 5. 为什么不把个人生活系统交给某一个 Agent 平台

用户最初提出私人助理时，就说各种 Bot 会不断更替，可能今天用一种，明天换成另一种。这意味着我们不能先选定产品，再把所有任务和记忆塞进它的内部。

这里真正需要长期保留的，是用户的目标、任务、规则、笔记，以及助理已经接受的责任。模型和消息平台只是处理这些内容的方式。

| 方案 | 开始时的便利 | 后来的代价 |
| --- | --- | --- |
| 全部使用某个平台自带的任务和记忆 | 接入快，现成功能多 | 更换平台时，要迁移的不只是文件，还有业务含义 |
| 全部从零开发 | 自由度高 | 很多通用能力也要自己维护 |
| 自己保存事实和业务规则，接入可替换模型 | 更换范围清楚 | 必须自己定义接口、权限和恢复方式 |

我们选择第三种。

这不是为了抽象而抽象。举例说，“已经完成”“今天暂停”“等材料到了继续”必须在平台之外有可查的记录。否则，换会话、换模型或重启以后，用户又要重新解释。

但解耦也有真实代价。自己的系统就要承担状态正确性，不能再指望框架替我们决定所有事情。因此，后来的框架选型，要看它能否接入这套分工，而不只是看现成功能有多少。

### 6. Pi 与 Hermes：当时为什么偏向功能更少的方案

早期讨论并不是直接否定 Hermes。聊天里比较的是两种不同使用方式：借助一个比较完整的常驻 Agent，或者使用较轻的 Agent 基础，再由自己的服务补外围能力。

当时讨论把 Pi 看作可以嵌入和扩展的基础，把 Hermes 看作带有更多常驻、消息、定时和记忆能力的宿主。记录中有官方资料查询，也有接口和功能比较；但没有找到两者同条件运行的性能试验。

| 当时的比较点 | Pi 路线 | Hermes 路线 |
| --- | --- | --- |
| 直接得到的东西 | Agent 调用、扩展和工具接入基础 | 更多现成常驻与外围能力 |
| 需要自己补的部分 | 调度、QQ适配、运行状态、权限等 | 接入自有业务规则，并厘清重叠职责 |
| 与自有任务系统的关系 | 边界较容易保持在外围 | 要决定自带调度和记忆哪些启用、谁负责 |
| 适合的前提 | 愿意维护秘书服务本身 | 希望尽量复用完整宿主 |

关键不在于谁“更强”，而在于我们已经决定自己管理什么。

如果任务状态、提醒规则和权限本来就要掌握在自己的服务里，那么框架额外提供的一些能力并不能直接算收益。它们可能还需要被限制，否则会出现两处都在安排、两处都在记任务的情况。

在这个前提下，Pi 的外围不足没有被当成根本障碍。用户了解这些不足以后，也明确接受自己补调度和适配的方向。

不过，这个判断依赖一个重要假设：自己补外围工程的成本是可以接受的。它不是已经证明 Pi 更便宜、更稳定，也不是说 Hermes 无法接入。如果实际接入成本超过复用收益，就应该允许更换。

这正是后续迁移可以发生的原因：早期选型是服务当时的分工，不是一种必须坚持到底的身份。

### 7. 从 Pi 到 AstrBot、NapCat：哪些理由明确，哪些不能替历史补写

用户后来明确提出，改用 NapCat 和 AstrBot，不再使用 Pi Agent 和原来的官方 QQ Bot 路线。这个选择可以在聊天中直接定位。

但“为什么换”不能简单写成“因为原方案不好用”。

在迁移之前，确实出现过读取文件、创建日记、确认任务和提醒不到的问题。可是这些问题并不都属于 Agent 框架。例如，Hello 提醒被保存成提案而未真正提交，是业务处理错误；仅更换框架不会自动纠正它。

因此，我们把这次迁移分成两个问题来研究。

第一，新的组合怎样分工。NapCat 处理 QQ 连接，AstrBot 及项目插件组织接入、模型和工具。它们不是两个和 Pi 完全同类的产品，不能把三个名字放在一起简单排名。

第二，哪些业务责任仍然不能外包给框架。任务是否成立、目录是否允许访问、提醒是否还有效、失败以后怎样恢复，这些依然由自己的服务负责。

| 方面 | 原路线：Pi＋官方 QQ Bot | 新路线：AstrBot＋NapCat |
| --- | --- | --- |
| 自然语言与工具 | 通过Pi及自己的适配组织 | 通过AstrBot和项目插件组织 |
| QQ连接 | 官方机器人接入方式 | 普通QQ账号登录后经NapCat接入 |
| 要维护的接口 | Agent适配、QQ协议与业务服务 | 插件、桥接、登录状态及组件兼容 |
| 业务状态与权限 | 仍需自己保证 | 同样仍需自己保证 |
| 不能直接推断的结果 | 不能因框架轻就认为总成本低 | 不能因接入现成就认为一定稳定 |

迁移过程的记录显示，开发中查看了 AstrBot 的插件、工具执行、模型提供者和消息接口，也处理了 NapCat 登录与部署。这些材料说明开发者研究了怎样把新链路接起来。

它们还不足以证明“新组合在所有方面胜出”。聊天中也没有明确留下用户将某个具体缺陷认定为迁移唯一原因的陈述。因此，这篇 ADR 记录明确选择和可解释的职责比较，不编造性能结论或隐藏动机。

我们实际接受的新代价，是普通 QQ 账号、扫码登录、连接维护和额外组件的升级兼容。要判断这次选择最终是否值得，需要看实际使用，而不是只看迁移代码是否写完。

### 8. 为什么先做 QQ，而不同时完成 Web、桌面和付费

讨论中曾考虑 Web 编辑。这个方向有实际原因：服务在服务器上运行，用户又不想通过 SSH 编辑文字，也不希望 Windows、服务器、GitHub 三端都要手动同步。

如果只看编辑体验，Web 是一个合理选项。问题是，当时更重要的助理闭环还没有稳定：能否听懂、能否实际落实、能否主动跟进。

| 首期范围 | 能解决什么 | 会挤占什么 |
| --- | --- | --- |
| QQ、Web、桌面一起完成 | 多端入口完整 | 认证、同步、界面、发布和兼容一起扩大 |
| 先做Web编辑器 | 写笔记方便 | 主动协作仍然需要另外完成 |
| 先做单用户QQ | 直接验证日常助理是否有用 | 编辑入口暂时受限 |

用户后来明确要求只管自己在 QQ 上使用，因此当前选择第三种。

这里没有否定 Web 的长期价值，而是区分“未来合理”和“现在必须”。首期先回答助理能不能真正减少负担，再决定值不值得扩展入口和商业功能。

已有的 Web 兼容实现也不因此需要全部删掉。当前不投入扩展，与破坏既有代码，是两件事。

## 三、数据：先避免两份真相，再考虑检索有多聪明

### 9. 脚本能提醒，为什么还讨论 SQLite

这是对话里反复推敲最多的问题之一。用户的质疑很直接：到点发消息，不就是运行一个脚本吗？有文档，为什么还需要数据库？

这个质疑是成立的。提醒本身不要求 SQLite。一个定时脚本读取 Markdown，然后调用发送接口，完全可以工作。

真正要补的问题出现在下一步：

- 脚本执行到一半服务重启，下一次怎么知道要不要再做？
- 同一条 QQ 事件到达两次，怎么避免建两个任务？
- 消息可能已经发出去，但回执丢了，是重发还是等待核对？
- 用户刚修改安排，旧提醒还能不能发送？

只要我们想可靠处理这些情况，就要保留某种可恢复的运行记录。数据库只是其中一种实现，不是唯一答案。

| 实现 | 可以做到 | 需要自己承担 |
| --- | --- | --- |
| 定时脚本，状态只在内存 | 简单到点执行 | 重启后很难确认此前效果 |
| 文档＋JSON/日志＋锁 | 能持久保存，也能做恢复 | 查重、并发、恢复顺序、清理需要自行维护 |
| 把全部正文和状态放进数据库 | 库内查询与事务集中 | 改变笔记使用方式，可能产生双份正文 |
| Markdown正文＋最小SQLite | 保留笔记形态，集中处理运行记账 | 文件和数据库之间仍需恢复设计 |

讨论曾倾向过脚本加日志，也曾把 SQLite 提前写成必选。用户继续追问以后，判断才逐渐收敛：不需要为了“像一个系统”而上数据库；但既然确实要处理查重、投递和恢复，SQLite 是单机情况下一个较小的实现选择。

因此最终接受的是最小运行库，不是第二个知识库。

这项决定不是“数据库比脚本好”。脚本负责执行，数据库负责记录，它们不是同一层的替代品。真正可比较的是：用文件日志自己管理状态，还是借助 SQLite 管理状态。

### 10. 为什么正文仍留在 Markdown

用户最反感的一种结果，是日记文件保存一份，数据库再保存一份全文。这样以后编辑哪一份才算数？如果不一致，谁覆盖谁？

因此我们先确定正文只有一个可编辑的真源：原 Markdown 文件。

数据库保存的是必要运行信息，例如一条入件是否处理过、某个消息是否待发、某项恢复操作执行到哪里。它不因为需要检索，就拥有另一份独立可修改的日记。

| 存储方式 | 便利 | 问题 |
| --- | --- | --- |
| 正文只在数据库 | 查询集中 | 削弱直接使用Obsidian和普通文件工具的体验 |
| 文件和数据库各有一份正文 | 两边都方便读 | 同步复杂，容易形成两份真相 |
| 文件为正文真源，索引可重建 | 人能直接用，派生数据可以恢复 | 索引和文件版本需要核对 |

选择第三种，是为了保留用户已经接受的文件使用方式。

这也意味着我们不能宣传“用了 SQLite，所以整个系统都原子一致”。SQLite 的事务不自动覆盖外部文件，更管不到 QQ。这一局限必须通过独立的恢复规则解决，不能靠更换存储名称绕过去。

### 11. 为什么只保留一个服务器工作副本

用户曾希望 Windows 可以写、服务器可以跑、GitHub 可以备份，而且不需要手工同步。直觉上，把三个地方都接到 Git 就能解决问题。

但 Git 更适合保存版本，不负责保证某个正在执行的任务只发生一次。两处都能修改任务状态，也不等于 Git 能理解“哪个安排才是当前有效安排”。

| 做法 | 使用上的好处 | 实际增加的问题 |
| --- | --- | --- |
| Windows和服务器都写，Git自动合并 | 本地编辑自由 | 正文、规则和机器状态可能一起冲突 |
| GitHub作为实时状态中心 | 云端有统一位置 | 拉取和提交不能代替运行中的事务及队列 |
| 服务器一个工作副本，Git只做可选备份 | 写入边界清楚 | 离线编辑要另外设计 |

当前采用第三种。

这个取舍并不完美，它暂时放弃了多处同时编辑的便利。但它让系统更容易判断某件事是否真的已经办成，也减少用户处理同步冲突的机会。

代码模板和私人数据也必须分开。公开模板仓库能发布，不意味着可以把服务器上的日记、登录数据或运行库一起推上去。备份是否真的可恢复，还要靠恢复操作确认，不能只看远端有没有一次提交。

### 12. 记忆不能只是一份越来越长的摘要

用户提出了一个很具体的例子：今天解释过的一个梗，后天换一种说法，助理应该还能理解。如果这个说法后来被实际复用，即使原聊天清理，也值得保留。

这里至少有三个不同需求：

1. 当前聊天能接上前文。
2. 一段时间后能找回具体背景。
3. 长期规则和共同语境不会因清聊天丢失。

如果只保存一份摘要，它可能越来越省字，但也越来越难知道哪句话来自哪里、什么时候适用、是否已经被更正。若把全部聊天无限保留，问题又变成增长、检索和删除的负担。

| 方法 | 得到什么 | 失去或增加什么 |
| --- | --- | --- |
| 原始聊天永久保留 | 细节最多 | 成本增长，相关信息仍未必找得到 |
| 不断覆盖一份摘要 | 体积小 | 来源、指代和更正可能丢失 |
| 随意追加多个记忆文件 | 写起来容易 | 可能写得到但查不到，也难处理冲突 |
| 近期对话＋有来源的长期事实 | 分别满足接话与长期使用 | 需要明确信息归属和有效范围 |

我们选择最后一种。任务和规则已有正式对象，就不再复制到背景记忆中。共同语境可以保存，但要知道是谁说的、对什么事情适用、后来有没有变化。

一个重要区别是：信息值得保留，不代表它已经被证实。模型自己反复引用某个猜测，不能把它“引用成事实”；用户没有反驳，也不等于同意。

这个选择的代价，是记忆系统不能只有“写入”和“搜索”。还需要更正、替代、失效和清理。否则记忆越多，旧错误反而越难消除。

### 13. 为什么暂时没有选择向量数据库

“记得住”很容易被直接理解成“需要向量数据库”。但本项目首先需要回答的是：到底找不到什么，为什么找不到？

如果用户说的是明确任务、某个日期或一份笔记路径，按对象和时间查往往更直接。如果用户换了一个说法，却指向同一个背景，语义检索可能有帮助。这两类问题不能只用一种技术想象解决。

| 方案 | 比较擅长 | 需要注意 |
| --- | --- | --- |
| 对象、日期、关键词查询 | 精确事项和已有引用 | 换说法可能漏检，需补查 |
| 嵌入与向量检索 | 主题近似、语义相似内容 | 相似不等于正确适用，也不等于当前有效 |
| 两者结合 | 兼顾精确和语义 | 多出索引、排序和维护路径 |

暂不引入向量数据库的理由有两层。

第一层是当前证据不足。聊天和设计材料里，没有一项完成的对照试验能证明关键词加模型补查已经不够用，也没有证明向量方案能稳定解决主要漏项。不能因为其他 Agent 常用，就先把它写成必要组件。

第二层是它不能解决当时更根本的问题。假如系统还分不清长期规则和猜测，不能让更正后的旧记忆失效，增加语义召回只是更容易找回这些内容，并不会让它们变正确。

所以，当前先把事实归属、来源、有效期和按需查阅做好，再看是否确实需要语义索引。

这也不是说向量库很重，或者永远不需要。语义检索还可以有不同实现，不一定等于部署一个独立服务。我们保留重新比较的条件：

- 真实的换说法场景持续漏掉关键背景；
- 模型补查仍不能解决；
- 新方案能在同一批样本里改善召回，同时不明显增加错误适用；
- 更正和删除能够可靠传播到索引；
- 收益值得额外成本和维护。

没有这些结果以前，结论只能是“当前暂缓”，不能写成“我们研究证明向量数据库不适合”。

### 14. 为什么“忘记”不是删掉一行

只要记忆会被摘要、模型上下文和后台作业使用，删除原文件里的一句话就不代表它已经停止影响系统。

例如，用户更正了一个长期偏好，旧作业却已经拿着原偏好准备安排。即使检索结果变了，旧作业仍可能继续提交。再比如恢复一个旧备份，把早已删除的内容带回来。

这里有两种不同承诺：

- 不再从当前记忆里搜索到它。
- 当前系统后续不再根据它行动。

第二种明显要求更多。

因此，选择把更正和撤销当成需要传播的变更：当前记录失效，相关摘要和候选失效，旧作业在使用前重新核对；恢复备份也要处理较新的删除记录。

这个选择仍有边界。如果系统只有一份很旧的备份，没有备份以后发生的删除记录，就不能凭空知道哪些内容不该恢复。可靠做法是限制旧记忆自动启用，并说明缺口，而不是宣称“删除永不复活”。

我们接受这种不那么好听的限制，是因为一个不能兑现的隐私承诺，比明确指出恢复条件更糟糕。

## 四、从“听懂”到“真正办成”，中间还差什么

### 15. 为什么理解交给模型，执行却不能完全交给模型

用户要求对话自然，不要依赖关键词，也不要固定脚本回答。这是因为真实表达经常带着省略、指代和修改。

“都确定，第二个改到下午”不是几个独立关键词。系统要知道“都”指哪一组，“第二个”是哪件事，“改到下午”是不是改变执行时间而不是截止时间。

固定规则可以覆盖少数说法，却很难覆盖所有语境。另一端，如果把所有操作都直接交给模型，又难保证它不会改错对象或越过权限。

| 方法 | 优势 | 无法独自承担的部分 |
| --- | --- | --- |
| 关键词路由和固定回复 | 可预测，实现快 | 开放表达、多事项、局部否定和上下文 |
| 模型直接操作所有文件和工具 | 灵活 | 权限、幂等、版本和执行结果 |
| 模型理解并选工具，服务核验并执行 | 自然交流与可验证后果能结合 | 需要把两者接口设计清楚 |

我们选择第三种。模型可以自主查阅、提出方案和调用工具，不必先被硬分成几个固定意图；服务负责检查对象、版本、授权和业务规则，再返回实际结果。

这里不能把服务夸大成“证明模型没有理解错”。它能发现对象不存在、版本变化或操作无权，未必能发现一个格式完全合法但意思理解错的要求。语义仍要用真实对话测试。

这也是为什么只改提示词不够。提示词可以告诉模型认真，工具和服务必须让它有办法查清楚，并让假成功没有机会被当成真实状态。

### 16. 从“不能读目录”里看见的，并不只是少了一个工具

用户多次要求列出仓库目录、读取本月计划，助理却说没有清单，需要用户提供。这个场景暴露了一个架构问题：模型只能看到服务预先塞给它的内容，不能自己补充调查。

有三种处理方式：

| 处理 | 眼前效果 | 后续问题 |
| --- | --- | --- |
| 每次预先把更多目录塞给模型 | 部分问题能答了 | 内容会过时，仍然可能缺文件 |
| 开放整个宿主机和Shell | 基本能找东西 | 权限远远超过用户授权的笔记范围 |
| 提供受控目录、搜索和文件工具 | 能按需查真实内容 | 需要做好路径、隐藏目录和会话权限 |

我们选择第三种。

目的不是限制助理只能读摘要，而是让它可以充分使用授权范围里的资料。安全不能通过“所有东西都不让读”来达成，否则系统也失去助理价值。

同时，读取普通笔记、修改业务状态、访问凭据是不同权限。笔记里的文字也不是新的系统命令。一个文档写着“忽略规则”，不能因此取得越界能力。

这一选择让我们认识到：能力和边界要一起设计。用户得到的是能查清楚的助理，程序承担的是路径验证、受控写入和真实部署隔离。

### 17. 一句“确定”为什么不能只是一个开关

用户希望经过一轮讨论，最后一句“就这样”就能落实当前几件事。早期体验却出现过只处理一项，或者又要求逐项确认。

如果把“确定”当作无条件开关，会有另一个问题：系统里可能还存在别的话题、过期提案和未讨论完的事项。它们不能一起被批准。

因此要保留的不是一个“用户说过确定”的标记，而是用户实际看过什么方案、每件事是什么版本、最后修改了哪里。

| 方式 | 优点 | 主要错误 |
| --- | --- | --- |
| 所有事项逐条再问 | 范围容易界定 | 用户已经决定还要重复操作 |
| 一句确定批准所有待定 | 快 | 可能批准无关或过期内容 |
| 结合已展示方案和上下文落实 | 接近自然协作 | 需要管理范围、版本和修订 |

当前选择第三种。清楚指向当前一组时就一起处理；真正不清楚时，只问那个不清楚的对象。

后面还要区分“接受了一组”与“所有操作必须同时成功”。两件独立的事可以一件成功、一件失败，但要分别说清楚。如果是互换两个时段，中间状态不能算最终冲突，两个修改应一起检查。

这个设计同时防止两种糟糕体验：一是用户被迫重复确认，二是系统为了显得能干而扩大授权。

### 18. Hello 提醒失败为什么改变了“成功”的定义

实际对话里，用户要求两分钟后发送 Hello，助理说建好了；到时间却没有消息。后来检查发现，只有待确认提案，正式任务和日程为空。

这个问题不能只归因于 QQ 不稳定。至少在这个案例里，系统连正式安排都没有生成，调度自然无从开始。

这里需要拆开的事实是：

| 当时的状态 | 可以说什么 | 不能说什么 |
| --- | --- | --- |
| 只是提出方案 | 有一份待定安排 | 已经建立提醒 |
| 业务已经提交 | 安排已经保存 | 一定已经发送 |
| 渠道返回接受 | 消息已交给渠道 | 用户已经读到 |
| 用户明确报告行为 | 用户说做过了 | 工具已独立验收全部成果 |

如果只让模型根据自己刚说过的话判断成功，它容易把“准备做”当成“已经做”。因此我们选择以实际提交和回执限制报告的内容。

这不意味着所有操作都要先问。用户明确交代“30秒后给我发Hello”，在范围和能力允许的情况下，应直接办理。额外制造提案又不落实，正是在增加用户负担。

这个案例的价值在于，它使“负责”有了工程含义：不能只语气认真，还必须知道实际效果到了哪一步。

### 19. 为什么日记必须通过统一模板生成

当用户追问“你会怎样建日记”，助理承认默认手写文件。问题是，现有模板不只是几段标题，还包含日期、周次、父级引用和上层重点。

如果模型照着外观模仿，今天也许看起来差不多，跨年或缺父级时就可能出现另一套规则。

| 方式 | 谁承担规则 | 用户体验 |
| --- | --- | --- |
| 模型手写类似文件 | 模型临时推算 | 快，但容易与原库不一致 |
| 用户先在Obsidian里创建 | 用户和桌面插件 | 规则一致，却打断QQ使用 |
| 统一模板能力供不同入口调用 | 系统维护一套规则 | 能自动创建，也能验证一致性 |

我们选择第三种。

统一模板并不意味着把已有日记重建一遍。文件存在就保留正文，父级缺失就按规则补，目标空白就留空。模板损坏或不受支持时，要说明没有建成，而不是降级为手写后报成功。

它看起来像一个很小的选择，实际上避免了“人用一套日历规则，AI又发明一套”的长期分裂。

## 五、持续推进：助理要负责，但不能强迫

### 20. 为什么用户任务之外，还需要记录助理自己的下一步

仅仅保存任务，仍然回答不了很多协作问题。

比如任务是“提交报告”，助理答应先帮找资料。任务还没有完成，但助理此刻欠下的事很明确。资料没到时，助理要等待某个条件；用户稍后回来，也不该再次解释它为什么在等。

如果只给任务加一个“进行中”，这些信息都容易散在聊天里。

| 办法 | 成本 | 不足 |
| --- | --- | --- |
| 只靠聊天记住 | 初始最少 | 清理、重启或换话题后容易丢 |
| 把助理准备也建成用户任务 | 看似统一 | 用户成果和助理工作混淆 |
| 记录独立的助理责任，引用原任务 | 增加少量状态 | 能表示下一步、等待谁和何时结束 |

当前采用第三种，架构中称为 Work。它可以简单理解为“助理还欠什么”。

一条责任必须能说明：下一步是什么，谁能推进，什么条件算完成。如果只是“核实材料存在”，检查通过后它就结束；只有原来还接受了整理材料的委托，才继续后面的工作。

这样做的目的不是让用户管理白板，而是让助理有自己的工作台。用户不必看到内部字段，但回来的时候，事情能接得上。

### 21. 前一晚安排，为什么还需要当天重新判断

用户希望前一天晚上把第二天确定好，第二天直接执行，减少重复决策。这是合理的，但现实不会按前一晚的假设完全运行。

六点起床的计划，可能八点才收到回应；任务可能比估计久；材料可能没到；也可能临时出现不能移动的会议。

如果系统机械把整天顺延，就会撞到固定事项。如果它每次变化都推倒重排，又让用户重新做所有决定。

| 处理方式 | 保住什么 | 容易损害什么 |
| --- | --- | --- |
| 固定不变 | 计划稳定 | 现实可行性 |
| 所有任务统一顺延 | 算法简单 | 固定预约、休息、截止和无关任务 |
| 从变化影响的部分开始重算 | 大部分计划继续有效 | 需要知道依赖和可移动范围 |

我们选择第三种。执行时间、预计结束和真正截止要分开；固定事项和休息先作为边界，再安排弹性工作。排不下时给具体缺口和建议，而不是暗自假定用户效率会突然提高。

缓冲也要说清楚。当前设计把默认缓冲作为可用时段末尾保留的时间，不是每件事之间必插一段；自动重排不能偷偷吃掉它。若确实需要减少保留，应有明确授权。

这个修正来自架构和测试对照时发现的矛盾：原案例要求把图表排到11:50，却同时应保留11:45以后的时间。发现矛盾后应改预期，而不是让实现自己猜。

### 22. 定时检查，不等于每次都要发消息

实际使用中，系统曾每两小时问一次“现在在做什么”，即使用户刚刚已经说过正在学习。

定时器没有错，它确实触发了。错在系统把“到检查时间”直接等同于“必须询问”。

| 联系方式 | 好处 | 问题 |
| --- | --- | --- |
| 每个时间点都发 | 不漏触发 | 已知答案仍问，打断和重复解释 |
| 完全不主动 | 安静 | 用户失联或受阻时没有外部支持 |
| 到点先查状态，再决定是否联系 | 信息不足时才问 | 需要判断已有信息的范围和有效时间 |

我们选择第三种。

如果刚才的反馈已经覆盖当前时段，就不再问同样问题。如果信息已经很久没有更新，又符合用户订阅的检查规则，可以核对。如果有新的截止风险或准备好的材料，也可能值得联系。

这一判断不能无限外推。用户说“七点起床”，不等于系统知道他十点在做什么；系统知道“开始学习”，也不代表知道“已经学完”。

所以主动性的衡量不是发了多少消息，而是在需要帮助的时候是否给了新的帮助。福格行为模型和情境适配研究为这种思路提供参考，但没有直接证明某个固定频率最合适。

### 23. 用户说“不想做”，为什么既不能立刻撤销，也不能机械劝坚持

这是自然助理体验里最重要的分歧之一。

如果系统立刻说“那就取消”，它可能放弃用户仍然认可的长期目标。如果系统永远说“先做五分钟”，它可能完全忽略用户已经决定放弃，或者根本不是时间长短的问题。

| 回应策略 | 看起来像什么 | 主要风险 |
| --- | --- | --- |
| 无条件同意 | 尊重用户 | 可能没有理解真实需要 |
| 无条件催促 | 有立场 | 越过明确决定，增加压力 |
| 先理解处境，再决定问、帮还是办理 | 需要判断 | 更依赖上下文，但符合实际协作 |

我们选择第三种。

已经知道材料不在，就先处理材料；重要任务原因确实不清楚，可以问具体问题；明确取消，就应该实际取消。不能假定助理比用户更知道“真正的你想要什么”。

“理解动机”也不意味着随意读心。模型可以提出一种解释，用来决定是否核对，但不应把它写成用户性格和心理事实。

用户希望助理有自己的立场，指的是认真把事情弄清楚、愿意提供实际帮助，不是让助理模拟生气、羞辱或情绪施压。

### 24. 为什么中文表达、分段回复和及时接手也属于设计

用户反感的不只是技术词，还有一种模式：长段解释、反复宣示原则、每次都加一个问题、对眼前的具体事却不作判断。

这说明自然表达不能靠换一个温柔人设解决。回复首先要有用途：回答当前问题、报告实际结果、说明必要影响，或者提出一个真正需要决定的选择。

简单事一条说完；慢工作可以先接手，后给结果；复杂变化可以分段。但不能为了像真人，随机等待、假装打字，或把模型内部思考不断发给用户。

如果用户在两段消息之间插话，后续内容要能根据新信息调整，而不是继续播放生成好的长文。若最终结果已经出来，排队的“我先看一下”就不该再发。

因此，语言和运行机制是连接的。只改句子而没有消息顺序、接续和失效处理，仍然会显得不像一个认真听话的人。

## 六、可靠性：不能让“看起来办了”替代实际状态

### 25. 为什么文件、数据库和QQ不能被想象成一个大事务

用户取消了一件事，系统至少可能要改任务、日记、后续责任和待发消息。中间失败时，不能简单说“整个操作都没发生”。

有几种办法：

| 办法 | 初始工作 | 出问题以后 |
| --- | --- | --- |
| 依次写完，失败再猜 | 少 | 很难知道哪些已经生效 |
| 所有正文移进数据库 | 库内事务方便 | 改变文件使用方式，仍管不到QQ |
| 正式提交可恢复，后续更新逐项确认 | 多一些状态 | 能保留已办结果并接着完成缺失部分 |

我们选择第三种。

可以把它理解为两件事。第一，正式记录要有恢复依据：如果写到一半中断，下次能核对当前文件，继续确定的操作或停止等待处理。第二，日记投影和待发消息等后续内容，要知道哪些已经更新、哪些还没更新。

这并不追求“任何时候所有地方都完全相同”。例如，任务已经保存，日记同步冲突，可以如实存在。关键是不能把没同步说成已同步，也不能为了修日记再建一次任务。

发送前还需要核对当前状态。否则取消通知还没来得及处理，旧提醒就可能发出去。后续协调负责及时更新，最后一次检查负责挡住过期后果。

### 26. 新消息来了，为什么不能只靠取消旧模型调用

真实对话会交错：用户先让安排下午学习，模型还在处理，用户又说下午有会。

如果新话已经进来了，旧安排还照样提交，体验显然不对。但如果每条新话都取消正在做的工作，用户连续聊天时，原来的合法事情可能永远做不完。

| 策略 | 保住什么 | 问题 |
| --- | --- | --- |
| 忽略新话，旧任务做完再说 | 执行顺序简单 | 可能继续执行已经撤销的要求 |
| 新话到达就全部重来 | 最新消息优先 | 无关闲聊也会打断原工作 |
| 先接纳新话，再按关联范围处理 | 安全与继续推进有机会兼顾 | 必须定义分类、提交先后和恢复规则 |

我们选择第三种。

新消息先保存，慢模型在锁外运行。尚未理解的新输入可能影响旧操作时，先暂停相关副作用；确认不相关以后，原工作应恢复。已经实际提交的结果不能假装没有发生，只能通过新操作更正。

这里的顺序看服务何时持久接纳、何时准备提交，不看聊天消息里一个可能延迟或回补的时间。

我们也接受一个边界：用户不断发来无法判断范围的全局修改时，系统不能同时保证旧工作立即执行、又绝不违反最新意思。它应该保存责任并说明阻塞，而不是为了看起来流畅偷偷忽略新话。

### 27. 不回复为什么需要从运行机制查起

实际使用中，用户多次反映 QQ 不回复。后来代码历史涉及循环阻塞、租约、作业截止和启动恢复。

这个问题给出的教训是：模型会说话，不代表系统能一直接话。

若接入、模型处理和投递全在一条必须等到底的链路上，一个慢调用就可能把后面的消息一起堵住。若超时只是界面上说结束，旧作业仍能返回并写入，也会产生另一种错误。

因此，选择把接纳、处理、提交和投递分开观察，给工作期限和当前执行资格。超时以后，旧结果不能继续凭过期资格修改状态；已经发生的效果仍要核对，不能盲重试。

这些机制不是为了让用户理解更多内部名词，而是为了让用户不用反复问“你还在吗”。界面上看起来简单的协作，恰恰依赖后台把中断处理清楚。

### 28. 成本为什么要由程序控制，而不是只告诉模型“便宜一点”

用户明确要求采用便宜的模型设置，曾关闭思考，后来又决定开启较低档思考。这个过程说明，目标不是单纯最便宜，而是在简单任务上避免不必要消耗，同时保留足够判断能力。

如果只在提示词里要求“尽量省”，模型仍可能反复查工具、纠错和生成长回答。失败重试也会产生费用，后台和前台共用额度时更容易失去控制。

| 控制方法 | 能做到什么 | 缺口 |
| --- | --- | --- |
| 只挑便宜模型 | 降低单次价格 | 调用次数和上下文仍可能失控 |
| 只提示少调用 | 有一定引导 | 不是可强制的预算 |
| 模型设置＋程序限额和结算 | 同时控制单次与总量 | 需要处理超时、无用量回执和重启 |

当前选择第三种方向。每次调用前检查预算，返回后结算；重试和思考用量不能忽略。回执缺失不能按零成本计算。

具体模型名、参数和限额应由实际配置与测量决定。聊天中选择了低成本方向，不等于证明某个参数在所有任务上最优。更换模型后，理解、工具选择和语言表现要一起重新检查。

## 七、我们接受什么未知，怎样继续做判断

### 29. 为什么不在这里罗列测试通过数字

这篇ADR的用途，是说明我们怎样理解问题、比较办法和作出选择。它不需要承担一份不断追加的运行报告。

某次测试通过多少项，离开代码版本和场景范围，很容易让人误以为整个助理已经成熟；罗列更多数字也不能代替理由。因此这里不保留运行证据清单，单独的运行证据文档也删除。

但这不意味着开发可以不验证。需要保留的，是每个决定能怎样被检验：

- 检查提醒，就看实际安排和发送，不能只看模型说建好了。
- 检查记忆，就看不同时间、不同说法、更正和撤销之后是否仍正确。
- 检查自然对话，就看是否接住全部事项，是否减少重复解释。
- 检查恢复，就在中间中断，而不是只演示正常路径。
- 检查长期价值，就看真实使用负担和行为，不能把在线时间当成果。

验证方法留在架构与开发流程里；ADR保留的是选择成立的理由，以及哪些结果会让我们改变选择。

### 30. 这篇报告里，哪些是历史事实，哪些是整理后的分析

这篇文章主要依据用户提供的聊天导出、当前架构及部分代码历史。它不是对每条工具输出的独立鉴定，也不是所有候选产品的性能评测。

有三类内容需要区分：

| 内容 | 例子 | 可以支持到哪里 |
| --- | --- | --- |
| 明确记录 | 用户要求取消评分、选择Pi、后来要求迁移组合 | 能确认当时表达和决定 |
| 根据记录整理的比较 | 为什么自有状态减少平台绑定、为什么多端写入更难 | 属于可讨论的工程推理 |
| 仍需验证的判断 | 语义检索是否值得增加、哪种模型更适合、长期行为是否改善 | 不能提前写成已经证明 |

特别是技术迁移，不能为了让项目故事更漂亮，把邻近发生的故障都解释成更换框架的原因。记忆方案也不能因为没有采用向量数据库，就倒推成我们已经研究证明向量方案不好。

对项目负责，既包括能提出办法，也包括知道自己的理由依赖哪些前提。如果前提变了，就应该调整选择。

## 八、后续决策怎样进入这一个ADR

以后不再为同一个问题另外建立一份研究稿。新的重要变化直接在本文对应主题补充：出现了什么新事实，原来的判断哪里不再成立，比较过哪些替代，最终怎样改。

一个值得留下的决定，至少应该让后来读到的人理解：

1. 当时为什么必须作选择。
2. 其他办法能解决什么，又会带来什么问题。
3. 为什么我们更看重其中某些条件。
4. 这个选择让谁少做了什么，让系统多承担了什么。
5. 什么事实出现以后，我们会承认需要改选。

本文仍保留“记录容易坚持、交代能够接续、对话自然、后果可靠”这条主线。具体技术可以改变，判断每次改变是否有价值的依据要保持清楚。
