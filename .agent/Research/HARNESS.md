# HARNESS｜让方法论成为系统的形状，而不是提示词里的句子（草案 v2）

v1 的方案是把五步六关写成常驻提示词。那是"塞进去"，已被否掉。本版换成结构性融入。

## 1. 判据：什么叫"融入"

同一个方法论，在系统里可以以四种形态存在，诱导强度依次上升：

| 形态 | 表现 | 模型能否绕过 | 例子 |
| --- | --- | --- | --- |
| 说 | 提示词里一句要求 | 能，且经常绕过 | "请先确认目标" |
| 问 | 工具参数必填 | 不能，但不填就编一个 | acceptance 字段 |
| 逼 | 填了会改变系统接下来做什么 | 不能，且编了会立刻错 | draft 不能排程 |

只有"问"和"逼"算融入。"说"是最弱的一层，因为它和上下文里所有别的要求抢注意力。

**融入 vs 塞进的分界线**：方法是不是变成了**现有动作的必填参数**。
- 塞进：新增一步"先写决策分析"→ 模型嫌麻烦就跳过，或写成套话。
- 融入：建任务这一步本身就要填"怎么算完成"→ 不填就没有任务。

**每个门禁都要满足三元组**：必填 + 诚实的"还不知道"出口 + 有后果。
- 缺必填 → 跳过；
- 缺出口 → 编造（LLM 会填一个看起来对的值）；
- 缺后果 → 当装饰，随手填。

## 2. 现状盘点：你的系统已经对了一半

对着真实 schema 逐层核过。

| 层 | 系统里的位置 | 必填 | 未知出口 | 有后果 | 判定 |
| --- | --- | --- | --- | --- | --- |
| 1 目标 | Task.outcome / acceptance | ✅ 非 draft 必须有一条 | ✅ draft 就是"还没想清" | ✅ draft 不能排程、不能提醒 | **对** |
| 2 现实 | day 记录、unreported、回执 | — | ✅ 有"未确认"状态 | ⚠️ 部分 | 基本对 |
| 3 卡点 | 症状分类（blocker.kind）＋判断（文本＋检查点） | ⚠️ 可空 | ❌ | **❌** | **空** |
| 4 取舍 | Proposal + accept/reject/defer | ⚠️ summary 可空泛 | ✅ defer | ⚠️ 只对"做/不做" | 半空 |
| 5 动作 | next_action / window / reflow | ✅ | ✅ | ✅ | **对** |

一句话：**动作层是结构化的，判断层是空的。所以它执行像样、判断像傻子。**

### 层 3 的确切漏洞

`blocker = { kind: time|scope|resource|ability|waiting|health|priority, detail, review_at }`。
全服务读过 `blocker.kind` 的只有两处：
- [planning.ts](.dev/secretary-service/packages/domain/planning.ts) 第 596 行：`priority` 时多问一句"保留、暂停还是取消"；
- [followups.ts](.dev/secretary-service/packages/domain/followups.ts) 第 244 行：`waiting` 时设检查时刻。

其余五个 kind 只进第 582 行的 advice 表，生成一句给模型看的建议文字，**不改变任何系统行为**。
一个填了没有后果的字段，模型必然当装饰——它的 kind 是随手挑的，于是"卡在哪一层"从来没被真正判断过。这就是"笨"的来源。

## 3. 最小改动集

不新增字段，只接线。这是本版和 v1 的根本区别。

### 3.1 blocker.kind 接成岔路口（必做）

现在：kind → 一句 advice 文本。
改成：kind → Core 的实际动作，模型下一条路被限定。

| kind | 现在的产物 | 应该变成 |
| --- | --- | --- |
| time | 一句建议 | 允许 reflow，只在已确认空闲内重排 |
| scope | 一句建议 | 只允许拆小步骤，验收快照冻结，不许降标准 |
| resource | 一句建议 | **不许重排**，要求补材料并给 check_at |
| ability | 一句建议 | 不许重排，要求换一条 next_action 且必须与原不同 |
| waiting | 设检查点 | 保持，并可要求给出不依赖回复的那部分 |
| health | 一句建议 | 减少弹性安排，保留休息时段 |
| priority | 多问一句 | 转成待取舍提案，不接受直接重排 |

改动量：一个按 kind 分派的函数 + 现有 reflow 入口的入参约束，不需要 schema 变更。

为什么这算融入而不是塞进：模型没有被告知"要区分客观机制和社会规则"，它只是发现——把"缺资料"报成"没时间"，Core 的回执就是对不上的。**一次就学会了。**

### 3.2 提案带"保留什么"（可做，但别加"排除"清单）

层 4 真正的缺口不是"没写不做什么"，而是**取舍没有牙齿**：提案可以接受一个会挤掉受保护时段的安排，Core 只在事后报冲突。
做法：提案附带 `keeps`（这次不能破坏的条件），应用时用已有的 protected / max_task_minutes / max_tasks 校验；破坏就拒绝并说明。
这样"优先什么、保留什么、排除什么"里的"保留"有了执行体，而不用逼模型写一段取舍论述。

### 3.3 层 2 不改结构

"把说法当事实"没有好的字段解法，硬加来源字段只会诱导编造。
它有现成的诚实出口（unreported / 未确认），剩下靠评测守。**这里必须忍住不加东西。**

### 3.4 层 3 不能被枚举（对 v2 的修正）

主要矛盾不是分类问题。1937 年判断"中日民族矛盾上升为主要矛盾、阶级矛盾降为次要"，这种判断不可能由任何枚举产生。
把五层做成枚举，等于用分类冒充判断，得到的必然是"主要矛盾：沟通不畅"这类填空。

层 3 要拆成两个承载：

- **内容**用文本：决策笔记或 Work.summary。允许复杂、模糊、保留多个候选，允许写"我还不确定"。
- **责任**用结构：Work 的 `condition`（可证伪的预期）、`check_at`（复查时刻）、`wake_on`（什么变化触发重判）、`prior_steps`（历次修订）。
  系统里已经有"可被证伪的判断"这个形状，不用新造。

对判断只固定六个问题，不固定答案的取值范围：

1. 候选有哪几个（至少两个）
2. 为什么是这一对压过其他
3. 主要方面是哪一侧
4. 若它成立，接下来应该看到什么
5. 什么条件下判断翻转
6. 何时复查

`blocker.kind` 因此降级：它是**症状分类**，属于层 2 与层 5 的接口，不是层 3。

**通用原则**：固定"必须回答什么"和"答完要过什么检验"，不固定"答案是什么"。

## 4. 六条习惯怎么分配

不是六条都能结构化。硬塞会把契约撑爆，反而更笨。

| 习惯 | 形态 | 落点 |
| --- | --- | --- |
| 求真 | 结构 + 评测 | 未知状态已有；不许把说法升格为事实靠评测 |
| 科学 | 结构 | 验收必须是可执行 checker（artifact_check 已是固定规则） |
| 系统 | 结构 | depends_on / reflow / effects 回执已在做影响链 |
| 结果导向 | 结构 | 状态机：开始 ≠ 完成；无验收不能 ready |
| 本质 | 产物 | 一句话机制，落在 Work.summary 或决策笔记，靠评测 |
| 辩证 | 产物 + 系统 | 系统侧的 accept/reject/defer 是外部对立面；反例靠评测 |

四条靠结构，两条靠产物。**不要试图把"本质"变成一个必填枚举**——那只会得到"本质：提升效率"这种填空。

## 5. 走查：用户说"我最近总是做不完"

全程没有任何一句话要求它"结果导向"或"找主要矛盾"，但：

1. 想建任务 → acceptance 必填 → 必须先问"怎么算做完"（层 1）
2. 想报阻碍 → kind 必选 → 必须归类（层 3）
3. 报 resource → Core 拒绝重排，回执要求补材料 + 检查时刻（层 2）
4. 若真相是"什么都想做完" → priority → 转成取舍提案，必须选保留/暂停/取消（层 4）
5. 接受后 → 只留一个 next_action 和一个窗口，其余进 draft（层 5）

形状把它推着走，而不是句子求它走。这才是"照着执行"。

## 6. 反模式

1. **契约膨胀**：一次加三个字段，模型开始填表，判断质量反而下降。
2. **强制即编造**：必填而没有"未知"出口，等于训练它说谎。
3. **两套流程**：五层是主干，别的理论只能挂到某一层，不能另起一套。
4. **把方法论当口号**：Any 出现在提示词里但不改变任何工具行为的词，都该删。
