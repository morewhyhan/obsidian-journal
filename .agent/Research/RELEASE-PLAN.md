# 私人助理：全局审计与发布收口计划

日期：2026-10-27。审计代码：`421bd20`。适用范围：单用户、QQ、AstrBot＋NapCat、DeepSeek、服务器上的唯一笔记副本。

**本计划的目标：让用户交代过的事情，在对话结束、计划变化、短期失联和服务重启后，仍有人准确接着处理。**

工程设计继续以 [ARCHITECTURE.md](ARCHITECTURE.md) 为基准。本文件规定下一轮如何实施、如何证明完成，不另建一套架构。不扩展 Web、收费、多租户和商业后台。

## 1. 结论：已有可用基础，缺的是完整责任链的可靠性

### 1.2 最重要的核心矛盾

**用户交付的是一件需要持续负责的事情；当前系统的可靠性仍主要按一次工具调用、一次对话、一个测试场景分别建立。跨阶段的责任没有处处接牢。**

因此会出现：能建任务，却不一定留下下一次处理责任；能记原则，却不一定改变后续安排；能生成回复，却不一定保证与实际执行一致；服务运行正常，却未必能按时完成完整工作。

最优先的工作是贯通：

```text
理解当前交代 → 对齐最新共识 → 保存承诺及责任
                         ↓
准备材料与下一步 → 到条件执行/联系 → 接收事实反馈
                         ↓
修正相关安排与旧提醒 → 保留未完成责任 → 下一次继续
```

每条箭头都要有真实数据、明确条件和失败去向。增加人格提示词、重复跑成功样本，都不能替代这条链。

| 编号 | 事实或风险 | 对用户的影响 | 处理包 |
| --- | --- | --- | --- |

## 2. 怎样才算做得好

### 2.1 把体验愿望变成验收要求

| 用户应该感受到 | 必须观察到的结果 |
| --- | --- |
| 我说正常人话就够了 | 同义表达、指代、修正、多事项、整体确认都能处理；无需工具名、编号或固定口令 |
| 交代一次，后面有人接 | 任务事实、下一步、负责人、等待条件和检查时机持久存在；换会话与重启仍接续 |
| 她会自己准备 | 在授权范围内查材料、定位上次进度、准备可执行下一步；找不到就明确缺口 |
| 有变化，她能处理 | 只调整受影响的依赖链和弹性安排；固定承诺、硬截止、验收要求不被偷偷改掉 |
| 我不必管理这个助理 | 不反复交代、不重复打卡、不手工修台账；技术故障不会转化为用户的日常管理任务 |
| 她懂得适可而止 | 提醒有实际帮助；沉默保持未知；暂停立即影响后续联系；回来不用补欠账 |
| 她说办好了就是真的 | 已接受、已提交、已投影、已发送分别核对；部分成功如实报告，重试不重复副作用 |
| 教过以后能改变做法 | 原则跨会话、重启和清理后仍可检索并正确适用；例外、撤销、范围明确 |

“有人愿意付每月 100 美元”是价值愿景，不能由测试数量推导。当前先证明可靠承接与减少协作负担；付费意愿需要后续真实用户选择，不能写成研发验收已通过。

### 2.2 保持的产品边界

1. 习惯记录约定行为是否发生；任务记录成果是否满足验收。投入时间、消息送达都不是完成。
2. 对话由模型自然生成，事实、权限、版本、提交和投递由程序校验。不能为了灵活而取消边界，也不能把自然语言变成关键词指令集。
3. Markdown 是正文唯一真源；复用现有 registry、Work、SQLite 运行状态，不新增第二套业务账本。
4. 日记通过现有模板引擎创建，保留用户正文、自然季度、跨年分段和父级引用。
5. 明确授权内直接处理；真正改变承诺时才带建议询问。沉默不能成为授权。
6. 支持用户行动，同时允许休息、跳过、暂停、改变目标。不能通过羞辱、依赖感或无限催促实现“主动”。

### 2.3 科学方法如何落到实现

福格模型用于检查动机、能力与提示是否匹配：任务难启动时先减小下一步，提示必须关联具体行动与时机。它是设计框架，不能据此证明“所有行为失败只有任务设计一个原因”。[福格行为模型](https://www.behaviormodel.org/home)

交互评审按初次使用、使用中、出错时、长期使用四个阶段进行，重点检查能力边界、低成本纠错和用户控制。[微软人机协作指南](https://www.microsoft.com/en-us/research/?p=564561)

工程采用“风险 → 可复现反例 → 最小修复 → 同类反例 → 发布观察”的顺序。逐步发布与回退用于控制测试无法覆盖的真实环境差异；单用户产品不伪装成有统计对照组的大规模灰度。[Google SRE 发布验证](https://sre.google/workbook/canarying-releases/)

## 3. 目标设计：用现有模块接成一个闭环

### 3.1 一件事只有一套有效事实

任务/习惯保留用户承诺与实际反馈；计划保留可变执行窗口；Work 保留助理还欠什么工作。三者关联，但不能互相替代。

每项有效责任至少能回答：关联哪件事、接下来谁处理、做什么、何时或在什么条件下再处理、什么证据算这一步完成。已有字段能表达就复用，不为每种场景新增一张表。

### 3.2 对话负责理解，提交负责兑现

模型读取当前共识和相关事实，提出成组操作。Core 检查真实来源、当前版本、作用范围及业务条件后提交，再把实际结果交给模型表达。

对于“就这样办”，解析最近仍有效的整组共识；对于“除了第二项”，只排除被明确修正的部分。有多个确实无法区分的方案时，只澄清对象。

需要持续处理的事项，其业务提交与接续责任必须同步建立或可恢复地关联。不能已回复“会跟进”，却没有任何后续触发依据。

### 3.3 后台工作和联系用户分别决定

满足工作条件即可在授权内准备；是否发消息再检查用户规则、静默、频率、有效窗口、当前进度与渠道状态。今天不提醒，不等于取消任务，也不等于禁止准备。

相关事实改变时重新检查责任；没有变化时不重复调用模型。旧计划、旧规则、旧委托的迟到结果不得覆盖新状态。

### 3.4 异常必须有明确去向

所有处理中断都落入以下一种可解释状态：安全重试、等待条件、等待用户必要决定、已被新要求替代、已终止、需要维护恢复。不能停留在“刚才出错了”而没有后续。

模型彻底不可用时，保住已提交事实，停止编造结果；已明确授权的原文提醒仍按规则处理。恢复后从真实结果接续，不重做已完成副作用，也不以固定安慰话术伪装正常助理。

## 4. 实施计划：八个工作包

路径均相对 `.dev/secretary-service/`。每包按“先留下失败证据，再修实现，再补回归”执行；已有通过且无关联变化的部分不重做。

### P0. 固定候选与验收依据

**目的：确定到底在验收哪一个系统。**

- 统一记录源码、依赖锁、工具契约、模板引擎、生效提示词、非秘密配置、模型 ID/思考参数、插件与容器 digest。
- 保留私人覆盖的语义，审计后去掉重复和过期指令；不直接用模板覆盖私人提示词。
- 审核 `scripts/release.ts` 的文件覆盖：当前扩展名筛选未覆盖 `.mjs` 与无扩展名的 Dockerfile。运行产物清单与测试脚本指纹分别登记。
- 建立一份机器可读验收矩阵：架构 I/Q/D、历史 A—K 用例、测试入口、候选指纹、实际结果、证据位置。没有映射的要求标未覆盖。
- 修正文档中“目标设计”“历史通过”“当前通过”混用及旧数字；不再并列多个互相矛盾的现状。

**位置：** `scripts/release.ts`、`compatibility-runtime.ts`、`scripts/evaluate-model.*`、Research 文档。

**通过条件：** 任意一个失败样本能定位到确切组合；缺场景、脚本中断、配置不符都不能生成全量通过结论。退出测试进程时可靠写出未完成项。

### P1. 把自然交代稳定转成有效共识

**目的：用户不用反复确认和纠正同一件事。依赖 P0。**

- 复用 proposal/decision/observed refs，明确讨论、整理确认、已接受、修订、撤销的边界。
- 对多事项确认、跨轮否定、迟到回复、指代和临时例外进行同义表达测试；不增加关键词路由。
- 先提供相关当前事实与共识，缺失再查；摘要不存在不能解释为事实不存在。
- 成组变更区分可原子提交的同一决定与独立事项；部分失败保留成功结果，错误不能覆盖真实状态。
- 所有成功回复来自实际执行回执。模型没有保存责任、工具拒绝或投影失败时，不能声称整体办好。

**位置：** `agent-runtime.ts`、`application.ts`、`read-stamps.ts`、`packages/domain/decisions.ts`、AstrBot 插件。

**通过条件：** 四件事讨论后一次整体接受，四件准确落实；期间修改一件，以最后要求为准；重复入件不重复建立；无法消歧只问一次必要问题。接受后的无变化次日不重新让用户决策。

### P2. 贯通主动准备、计划和责任接续

**目的：一轮对话结束后，工作继续。依赖 P1。**

- 接受需要跟进的事项时，确定性建立或关联 Work；不完全依赖模型额外记得调用一次 `save_work`。
- 将周期规则、日期/周期与责任使用稳定身份关联；重启和重复检查不重复建下一天。
- 补齐 `wake_on`：相关对象变化、匹配反馈、约定时间、等待条件解除。相关变化可立即重新评估，未到固定检查时刻不应掩盖应响应的事件。
- 复用现有模板、排程和 reflow 实现，接入受限委托；为 `create_period`、`reflow_flexible` 明确对象、日期、路径和不可改变的承诺。
- 前夜按索引补齐必要上层及次日日记；参考有效上层重点与当日事实，不虚构空白目标。已接受工作延续，有必要取舍才询问。
- 超时只重排相关弹性安排与依赖；重新检查固定事项、休息和硬截止，撤销旧提醒。准备完成与用户任务完成分开。
- 周/月/季/年转换检查方向、容量和未决事项，不复制下层全文；重叠周期合并为一次有用沟通。

**位置：** `work-runner.ts`、`work-checks.ts`、`background-grant.ts`、`coordinator.ts`、`assistant.ts`、`packages/domain/work.ts`、`followups.ts`、`planning.ts`。

**通过条件：** 断开聊天后仍能在约定条件执行；参考材料变化能唤醒；等待解除能继续；过期授权不能提交；重复触发和崩溃恢复只产生一次有效结果；晚间规则改为 20 点后旧 21 点触发失效。

### P3. 收敛上下文、费用和模型失败

**目的：自然能力在真实预算内稳定工作。依赖 P0，可与 P2 并行。**

- 将 N06 等失败分成输入超限、模型服务失败、错误工具选择、未保存责任、事实表达错误和测试器错误，逐项保存证据。
- 精简固定提示词；使用相关片段、分页和真实工具结果摘要。保留权限与当前承诺，不能为省 token 裁掉关键约束。
- 启动期提示词占比检查只作早期保护；必须验证工具定义、当前状态、多轮结果和输出预留合计的实际容量。
- 结构纠错、重读和提供方重试有界，所有物理调用记账；重启与换会话不清零；成功副作用不可因表达失败而重做。
- 连续运行同一个“30 条有效入件参考日”，包括后台准备、提醒表达和一次合理失败；不能每场景换空库重置预算。
- 记录请求数、输入/输出/思考 token、缓存使用与延迟。金额按当时已核实价格计算；当前提高后的生产额度是待验证配置，不继续静默加码。

**位置：** `model-budget.ts`、`model-job.ts`、`token-counter.ts`、`agent-client.ts`、`compatibility-runtime.ts`、插件 `model_contract.py`。

**通过条件：** 固定组合下关键真实模型场景达到架构三轮完整通过；所有失败仍保留。参考日不靠临时加额度完成；耗尽测试能正确降级且不丢事实。三轮通过只证明这批样本，不宣传为任意表达必然正确。

### P4. 保护事实、清理和恢复

**目的：出故障也不丢承诺、不重放旧动作。依赖 P0。**

- 先复现“不可信时钟＋清理”风险；破坏性清理必须使用可信时间与安全防重边界，不可只停止水位推进。
- 在提交前、文件写入后、应用完成前、回复前分别中断，验证恢复后事实一致；旧作业、旧版本与重复回执不能覆盖新状态。
- 检查活动任务、Work、规则、未完成提交、费用预留的清理保护。把长期必要事实与短期会话分开，避免永不清理全部历史。
- 将现有 SnapshotBackup 接入部署：库外备份目录、独立密钥、定时运行、结果与过期告警；密钥不进入备份包或 Git。
- 配置独立故障域副本；没有异地目标时明确此项阻塞，不能把同盘目录称为灾备。保留 Git 默认关闭的现有边界。
- 首版采用可验证目标：日备份 RPO 不超过 24 小时；有可用空主机及必要凭据时，恢复到可检查状态 RTO 不超过 60 分钟。QQ 重新登录另计，不能混入已恢复业务状态。
- 恢复到空目录后先关闭旧投递和付费调用，检查完整性、预算及恢复边界，再显式解除必要保护。不得恢复积压消息后集中补发。

**位置：** `maintenance.ts`、`retention.ts`、`store.ts`、`recovery-control.ts`、`snapshot-backup.ts`、`deploy/compose.yaml`、CLI。

**通过条件：** 时钟前跳/回拨不提前删事实、不重置预算、不重放；错误密钥、损坏包、路径穿越整包拒绝且目标无半成品；快照恢复后正文、事实、规则、提示词一致。实测并记录 RPO/RTO，未达目标不得报达标。

### P5. 完成真实负载、故障和运行保护

**目的：后台不拖垮对话，维护不偷偷耽误提醒。依赖 P2—P4 的相关改动。**

- 按 ARCHITECTURE §4.3 构造完整参考数据，不止笔记文件：任务、习惯、Work、安排与规则同时存在。
- 测正常入件、1 分钟 10 条突发、慢模型、渠道断线、预算耗尽、维护与到期提醒重叠；分别报告结果。
- 验证一个模型槽的公平性、有界队列、后台同机会合并与两次尝试限制；已接纳事项不能静默消失。
- 对同步清理/快照实测事件循环停顿与持锁时间。超预算就分批，或明确进入排空维护；不为解决停顿引入额外微服务。
- 监控区分进程存活、Core 可办理、模型可用、QQ 在线、最老待处理年龄、投递未知、备份陈旧与资源占用。`/healthz` 成功不等于渠道正常。
- QQ 断线不能靠 QQ 自己报警；提供独立维护检查入口。容器升级保持 NapCat 登录卷，固定待发布镜像 digest，不随意重建已登录实例。
- 复查本人/机器人身份、群消息拒绝、提示注入、越界路径、链接、秘密脱敏、恢复包与依赖风险；不放宽文件隔离来修功能。

**位置：** `scheduler.ts`、`core.ts`、`model-job.ts`、`app.ts`、`log.ts`、部署自检及性能脚本。

**通过条件：** 采用架构原有阈值：本地查询/接纳/小型提交 p95≤250ms；就绪内部派发 p95≤2s、最大≤5s；Core≤512MiB。分位数至少 100 样本；另列故障和维护的总用户等待、失败及最大值。超包络明确降级，不裁数据制造通过。

### P6. 跑完整使用过程，而不只跑接口

**目的：证明像助理一样工作。依赖 P1—P5。**

- 用第 5 章矩阵映射原 A—K 用例。相同机制复用参数化测试；不同后果不能因为名字相近合并掉。
- 保留现有 38 个真实模型场景并修复未完成轮次；补自然改写、不同任务名、相反合法规则与未参与调试的留出表达。
- 同一份库跑跨日剧情、长对话和时间推进；比较真实状态变化、文件、触发、投递，而非只检查回答关键词。
- 真实 QQ 验证：承接→办理→定时出站→反馈→日记→取消/更正→重启接续。实际登录与外部投递证据单独记录。
- 故障注入先用隔离库和录制渠道；真实个人库只做已授权、可回收的验证，不能拿私人数据做破坏性实验。

**通过条件：** 高后果错误为零；关键剧情全部达到后置条件；正常支持场景不出现要求用户重复全部信息、无必要再确认或虚假完成。测试中断、环境故障和缺证据分别标记，不能按成功处理。

### P7. 发布、观察和最终交接

**目的：完成能维护、能回退的实际交付。依赖 P6。**

- 固定候选，导出快照和兼容回退材料；测试旧镜像面对新数据的真实兼容性。不可逆数据变化使用向前修复，不以旧快照覆盖用户新记录。
- 一次只切一套写入者；上线后核对完整指纹、接纳、合法文件读取、一个业务闭环和既有安排。防止双调度。
- 连续观察至少 7 个真实日，覆盖工作日与周末；出现高后果错误暂停扩大使用，修复后重验受影响门禁。
- 30/90 天观察按真实日历继续记录，时间推进测试另列；未到期时标“观察中”，不能提前宣称长期有效。
- 输出简明的启动、升级、扫码恢复、备份恢复、暂停/停用说明与验收矩阵。模板不带个人数据、密钥、真实聊天或运行数据库。

**通过条件：** 第 7 章所有适用门禁有证据，剩余限制明确；无需开发者日常手工改台账才能正常使用。涉及真人行为稳定性的结论只报告实际观察。

## 5. 用户全生命周期与异常覆盖

### 5.1 用情境维度覆盖，而不是无穷枚举句子

每类至少覆盖正常路径、拒绝/中断路径、恢复路径；高风险类别再组合测试。输入表达可以变化，事实标准不变。

| 场景组 | 必须包括的情况 | 严格后置条件 |
| --- | --- | --- |
| 初次使用 | 空库、模板空目标、缺可用时间、能力询问 | 可解释真实能力；只补问影响行动的条件；不把示例当承诺 |
| 承接与确认 | 一句话多事、先讨论、整体接受、排除一项、连续修正、引用别人话 | 各事项有准确去向；最后明确要求生效；引用不变授权 |
| 时间与周期 | 相对时间、跨午夜/月/季/年、时区变化、工作日例外、夏令时歧义 | 发生时间、计划窗口、硬截止分别正确；歧义才确认 |
| 日常执行 | 未开始、开始、部分完成、习惯最低行为、任务验收、投入时间 | 各事实不混淆；不为补齐字段强行追问 |
| 计划变化 | 起晚、超时、插入急事、依赖受阻、固定预约、休息、无可行解 | 只改受影响内容；授权内办，必要取舍带建议问 |
| 反馈与更正 | 昨天的反馈今天到、回复旧提醒、同名任务、记错、手工勾选 | 归到正确对象与日期；撤销错误后果；保留正文 |
| 沉默与回归 | 两小时不回、一天不回、十四天不回、连续未推进 | 未知不等于失败；依规则联系；回来从当前接续，不补催积压 |
| 学习与偏好 | 长期原则、仅今天例外、撤销、反义规则、跨任务适用、不适用 | 会记、会找、会用；规则到期正确；撤销后不复活 |
| 自主支持 | 找材料、准备下一步、材料失效、无思路、长期不动 | 支持针对真实障碍；不编资料，不擅自降低成果或贴性格标签 |
| 沟通控制 | 暂停此事、今天不联系、长期关闭、恢复、改时刻、专注中 | 范围准确；旧动作失效；准备与联系按各自授权执行 |
| 故障与恢复 | 重复入件、乱序、回复丢失、投递未知、模型超时、磁盘满、崩溃 | 保住事实、有界重试、无重复副作用；不能说成功掩盖失败 |
| 安全与退出 | 非本人、群消息、笔记注入、越界、导出、删除、停止运行 | 无权限扩大、无秘密泄漏；停止后无幽灵提醒，备份删除边界明确 |

### 5.2 六条必须贯通的剧情

1. **正常一天：** 前夜讨论并整体确认四件事 → 模板建日记 → 无新聊天仍准备 → 按时支持 → 反馈 → 验收 → 次日接续。
2. **被打乱的一天：** 晚开始＋任务超时＋依赖＋固定预约 → 局部调整 → 必要取舍 → 旧提醒取消 → 有效计划一致。
3. **教过以后的一周：** 教原则 → 同义情境适用 → 今天例外 → 次日恢复 → 不适用情境 → 重启 → 原错误场景不复发。
4. **失联后回来：** 14 天无反馈 → 渠道中途断线 → 不臆测行为 → 恢复登录 → 不集中补发 → 从当前承诺恢复。
5. **九十天项目的时间推进：** 分阶段、受阻、改优先级、清理、升级、恢复、验收收尾；活动依据不断链。明确这不是九十天真实运行。
6. **一次故障的完整恢复：** 提交成功但回复失败 → 重启 → 用户问是否办好 → 查真实结果回答 → 不重复执行；再验证快照恢复后的旧消息保护。

## 6. 什么才算测试通过

### 6.1 判定顺序

每次验证依次检查：输入与授权 → 实际业务状态 → 文件/投递副作用 → 恢复后状态 → 用户回复。前面失败，后面说得再好也不通过。

每条用例必须写明前置数据、输入、允许动作、禁止动作、后置条件、证据和清理方式。不能仅断言“返回 200”“工具被调用”“文本含已完成”。模型可以辅助评语言，不得单独裁决事实、权限和财务用量。

### 6.2 三种证据不得互相替代

| 层次 | 证明什么 | 不证明什么 |
| --- | --- | --- |
| 确定性/故障测试 | 业务规则、事务、边界、恢复、时间推进 | 模型理解真实自然语言的稳定性 |
| 真实模型＋录制渠道 | 给定组合下的语义、工具使用、预算与多轮协作 | QQ 真实投递、账号状态和真人价值 |
| 真实 QQ＋实际使用 | 集成链路和观察期间体验 | 所有未来情况、九十天效果、普遍付费意愿 |

### 6.3 重跑纪律

失败保存原样，先判断根因再修。相同版本反复运行直到挑到三次成功，不算三轮验收。固定候选后预先确定三轮完整范围，所有尝试纳入记录；发生改动则建立新候选，重验关联范围及关键完整剧情。

未执行、被环境阻断、测试器错误、产品失败、通过分开。提供方异常属于依赖故障证据，不能从用户成功率分母中偷偷删除；同时单列其责任归属。

## 7. 发布门禁与实际价值

### 7.1 发布前必须关闭

- [ ] P0 组合固定，证据可追溯，无缺项冒充全量。
- [ ] P1/P2 自然确认、持续责任、准备与联系、变更撤销贯通。
- [ ] P3 真实模型完整验收与连续参考日预算通过。
- [ ] P4 数据恢复、可信清理、自动且独立的备份实测通过。
- [ ] P5 参考负载、故障保护、身份与文件边界通过。
- [ ] P6 六条剧情及真实 QQ 关键路径通过。
- [ ] P7 发布、回退、停用和维护说明可由另一名执行者完成。

以下任一出现均阻止宣称发布完成：越权、丢事实、错误归属、虚假完成、错误扩大授权、未停下的已取消提醒、重复副作用、无法恢复、超预算绕过保护。不能用总体通过率抵消。

### 7.2 运行观察与价值观察

上线七日记录实际天数、交代数、无必要追问、重复交代、错误更正、手工修复、过期提醒、响应与完成等待、模型成本。不额外要求每日评分，也不把未知行为补成失败。

严格体验底线：验收剧情中无必要重新交代为零；发布观察中高后果错误为零；发现一次流程性重复劳动就进入缺陷单，说明影响范围与修复证据。普通措辞偏好可后续改，不让它掩盖可靠性问题。

价值分别看三件事：系统是否可靠运转、用户是否减少管理负担、目标行为是否更稳定。后两项需要实际使用证据；习惯记录只能支持观察，不能单独证明因果。

工程门通过可以宣布“此单用户 QQ 版本达到已列明发布范围”。真实 30/90 天观察尚未结束时，只能附“长期观察中”。如果 ARCHITECTURE 的完整完成定义要求这些证据，则其 G 门保持未关闭，不能改名偷偷绕过。

## 8. 给下一位执行 Agent 的交接

### 8.1 开始顺序

1. 阅读本文件及 ARCHITECTURE；检查工作区与线上组合是否已变化，保留用户改动。
2. 先完成 P0，并将本计划 F1—F8 转成可复现证据。未复现的风险保留待核验，不凭推测改大架构。
3. P1→P2 为主线；P3、P4 可独立实施，涉及共享提交和授权接口时先统一合同。
4. 完成 P5，然后固定候选执行 P6。只为实际失败扩展验证，避免重复无效跑全套。
5. 按 P7 发布与观察；没有部署、密钥或异地存储输入时，完成所有独立工作，再集中列真正阻塞。

### 8.2 每个工作包交付同样五项

**失败证据、最小代码改动、有效回归、用户结果证据、剩余边界。**

记录在一份验收矩阵与 DDD 当前实施记录中，不再新增十几份互相覆盖的报告。运行日志和真实聊天留在受保护证据目录，Git 只保留脱敏摘要与可复现步骤。

### 8.3 收口纪律

保留现有模块与数据模型；优先修接口之间的断点。不要为了“完整”增加消息队列服务、向量数据库、多 Agent 编排平台、任意脚本执行、收费系统或 Web 重做。

本计划完成的标志是每项已接受责任都能追踪到真实去向、异常能恢复、用户无需反复维护助理，并有对应证据。文档数量、代码行数和测试数量都不作为完成替代品。

## 9. 补充审计：为什么说话与调用不自然

本节依据 2026-10-27 对当前提示词、上下文及实际回复路径的追加静态检查。说明代码中的机制和可检验的风险，不将其直接冒充每条线上怪异回复的已证实原因。本轮发现工作区已有其他开发改动，未覆盖、未修改业务代码。

### 9.1 两种不满存在共同根因

事情接不下去，是责任连续性不足；对话像拼接，是共同语境和表达连续性不足。两者都要求系统持续知道：正在谈哪件事、已经说定什么、刚才发生什么变化、还欠用户什么。单独增加人格描述无法建立这些事实。

### 9.2 已核实机制与最小修改

| 机制 | 当前代码证据 | 应怎样修改 |
| --- | --- | --- |
| 新旧指令并存 | 库内 `.agent/prompts/system.md` 仍要求通过 `submit_proposal` 交业务变更；`execution.md` 与插件 native 分支要求工具环内执行、直接自然回复 | 为实际执行模式生成唯一有效协议；保留私人偏好，去掉旧协议与重复补丁；发布前检查冲突，不靠追加一句覆盖所有旧要求 |
| 最终改写缺少直接语境 | 插件 `main.py` 的语言改写只传 request、draft、observed_tools；没有直接传第一轮的当前共识、近期对话及完整相关偏好 | 优先让执行模型在真实回执后完成表达；确需独立表达时传小型沟通上下文：当前议题、已说定内容、变化、实际结果、必要决定和语言偏好 |
| 改写仍背负执行说明 | 只负责措辞的调用依然加载全部 `payload.instructions`，其中包含工具和业务协议 | 表达阶段只接收角色风格、事实边界和沟通任务；执行契约留在执行阶段，避免模型用程序术语组织普通对话 |
| 工具发现成本偏高 | `model_contract.py` 压缩动作 schema；`main.py` 要求具体动作首次使用先查 capabilities，再提交 | 在现有合同上按当前任务提供少量相关完整动作定义，并做会话内缓存；未知能力仍可查询。不能将全部动作每轮塞满，也不改成关键词识别意图 |
| 近期消息容易被误当共同理解 | `core.ts` 预载最近六条已处理入件，并裁剪各条长度；虽有进一步查询工具，仍依赖模型主动补查 | 复用已有 proposal/decision/Work 生成当前议题与最新共识视图；说明预载范围，缺失时定位查询。不得新增另一套权威任务库 |
| 风格检查与效果检查脱节 | native 路径已有二次改写及多条“自然、简短”要求，说明再加相同指令不能解决结构问题 | 用连贯对话评测指代、必要确认、结果准确性与回应贴切程度；长度只是参考，不用一两句硬限制多事项核对或复杂解释 |

说明：普通前台 `tools-v2` 已直接走 `processNativeInput`，不会执行后面的旧关键词分支。因此不能根据仓库里还存在关键词代码，就断言当前全部对话仍靠关键词路由。旧后台提案路径与正式委托路径的职责差异，仍按 P2 统一核验。

### 9.3 给模型的是工作语境，不是让用户阅读的程序日志

Core 保留完整审计结果，对模型提供两种不同视图：执行视图包含必要 ID、版本与可执行合同；沟通视图包含用户关心的对象、时间、变化、实际结果、未决条件。二者来自同一事实，不另存互相冲突的正文。

例如，计划实际改好后，可以表达“报告留到 11:20，图表接着做，下午会议不动”。若只是建议，则必须表达为建议；若只改成功一部分，则指出未改好的部分。自然语言不能掩盖状态差别，也不必把“投影、委托、门禁、作用域”等内部名词搬给用户。

### 9.4 收口方法与通过条件

按 P0 固定有效提示词 → P1 整理当前共识 → P2 贯通执行与责任 → P3 简化工具与表达调用 → P6 连续对话评审的顺序完成。

选择真实失败对话并脱敏，加入同义改写和新情境，验证：

1. 同一议题跨多轮、插入闲聊后仍接得上；不重新要求用户交代已有信息。
2. “就这样”“第二个先别做”“还是按刚才的时间”等表达能指向正确版本和对象。
3. 工具字段错误在权限与预算内自行纠正，不把内部协议问题反复交给用户。
4. 普通办理回答实际变化，复杂问题保留必要细节；无无关能力清单、机械邀约与重复免责。
5. 二次表达若保留，不丢失失败、未知、时间、数量和原承诺；若取消，不降低事实准确性。比较相同样本的质量、耗时与调用成本后决定。
6. 人格表现来自记得事情、判断恰当和帮助落实。亲近口吻不能靠虚构关系、假装生气或情绪施压实现。

将事实准确、任务接续、沟通自然分别评价。语言流畅不能抵消漏办，工具正确也不能抵消反复让用户费力解释。只有三者共同通过，才算本节收口。
