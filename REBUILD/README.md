# 重构工程

> 目的：保留当前版本作为可回看的基线，从已经暴露的问题出发，重新设计并实现私人 AI 助理。
>
> 本目录不是新的产品说明，也不是旧架构的复制品。它是重构过程的控制文档：先把问题、边界和验收写清楚，再开始写代码。

## 1. 重构的起点

当前仓库包含三类内容：

1. 可继续使用的 Obsidian 模板和私人笔记结构。
2. 已经开发过、但仍有行为缺陷的助理服务。
3. 多轮讨论后形成的架构、领域和决策文档。

重构不是把所有内容删除后重新猜一遍，而是：

- 保留模板和历史记录的兼容边界；
- 把当前软件作为旧实现，先冻结、标记和验证；
- 重新确认用户要得到的行为；
- 用新的领域模型、技术合同和可观察测试逐步替换旧实现。

旧代码不能因为“准备重写”就被当成正确实现。旧代码只提供证据，新的设计才决定未来怎么做。

## 2. 仓库管理方法

### 2.1 分支和标签

| 名称 | 作用 | 规则 |
| --- | --- | --- |
| `master` | 已保存的稳定基线 | 只接收已经通过当前验收门槛的提交 |
| `rebuild` | 新架构的重构主线 | 从重构快照开始，不直接覆盖旧基线 |
| `rebuild/<slice>` | 一个可验证的垂直切片 | 一次只解决一个用户可观察的问题 |
| `pre-rebuild-YYYYMMDD` | 重构开始前的不可变快照 | 只用于回看和恢复，不在上面继续开发 |

重构开始前必须完成一次提交，并打一个快照标签。这样“推倒重做”不会变成不可恢复的覆盖操作。

### 2.2 提交规则

一次提交只表达一个完整意图：

- 一个领域规则；
- 一个接口合同；
- 一个用户流程；
- 一个故障修复；
- 或一次经过验证的文档变更。

提交前必须说明：

1. 解决了什么用户问题；
2. 修改了哪些边界；
3. 用什么命令或测试验证；
4. 还有哪些没有验证。

不能把“重构、改提示词、改数据库、改部署”塞进一个无法回退的大提交。

### 2.3 仓库卫生

以下内容不得进入 Git：

- QQ、模型、Git 的密钥；
- 私人日记、运行数据库、聊天日志和备份；
- `node_modules`、构建产物、测试缓存和临时压缩包；
- 生产环境的真实配置。

每次推送前检查：

```text
git status
git diff --check
git diff --cached --name-only
```

发现不确定的文件时，先停下来确认归属，不用 `git add .` 代替审计。

## 3. 重构时采用的方法

### 3.1 先描述问题，再描述方案

每个重构事项先写清楚四件事：

| 项目 | 必须回答的问题 |
| --- | --- |
| 现象 | 用户看见了什么错误或负担？ |
| 根因 | 哪个边界、状态或数据关系导致了它？ |
| 目标 | 改完以后用户能观察到什么不同？ |
| 验证 | 什么输入、状态和结果算通过？ |

没有这四项，不开始写代码。

### 3.2 先画边界，再写模块

模块按业务规则划分，不按文件、工具、模型或线程划分。

每个模块必须说明：

1. 它解决哪一个稳定问题；
2. 它拥有哪几个对象；
3. 哪些不变量只能由它保证；
4. 哪些事情明确不归它负责；
5. 其他模块通过什么命令、查询或事件与它连接。

如果两个模块都能修改同一个业务事实，说明边界还没有划清楚。

### 3.3 先写行为验收，再实现

每个垂直切片按下面顺序进行：

```text
用户场景
  ↓
可观察的失败测试
  ↓
最小领域规则
  ↓
应用层连接
  ↓
基础设施适配
  ↓
真实入口验证
  ↓
提交并记录证据
```

测试关注用户能看到的结果，不以“某个函数被调用”作为完成标准。

### 3.4 优先做纵向闭环

不要先把所有领域类、接口和基础设施一次写完。优先完成一条最小闭环：

```text
QQ输入
  → 理解一件明确的事
  → 保存一个业务事实
  → 产生一个可检查的后续状态
  → 返回真实结果
```

闭环通过后，再扩展到多事项、排程、提醒、日记投影和长期记忆。

## 4. 重构阶段

### P0：冻结旧基线

- 提交当前工作区；
- 创建 `pre-rebuild-YYYYMMDD` 标签；
- 记录当前已知问题和未验证项；
- 排除密钥、私人数据和测试缓存。

### P1：重新定义产品

- 明确用户真正要减少的负担；
- 明确助理负责什么、不负责什么；
- 区分习惯、任务和助理责任；
- 写出三到五个最重要的真实使用场景。

### P2：重新设计领域

- 建立术语表；
- 划分限界上下文；
- 定义聚合、不变量和生命周期；
- 定义上下文之间传递的引用、版本和回执。

### P3：重新设计应用合同

- 定义一次用户输入的接纳、理解、查询、提交和回复顺序；
- 定义模型可以建议什么，Core 必须强制什么；
- 定义并发输入、取消、重试和失败恢复；
- 定义哪些操作需要用户决定。

### P4：实现最小可靠内核

- 先完成单写者、版本、幂等和事务边界；
- 再接入调度和消息投递；
- 再接入 Markdown 和日记投影；
- 最后接入长期记忆、复杂排程和自然表达。

### P5：按用户场景扩展

每次只增加一个闭环：

1. 单事项交代；
2. 多事项交代；
3. 修改已确定安排；
4. 延误和冲突处理；
5. 助理责任持续跟进；
6. 日记和周期计划联动；
7. 长期规则和偏好复用。

### P6：验收和发布

- 隔离测试通过；
- 真实模型测试通过；
- QQ 真实联调通过；
- 重启、重复消息、人工改文件和失败恢复通过；
- 明确哪些能力仍未验证；
- 通过快照和回滚方案后再发布。

## 5. 文档怎样组织

重构期间，正式文档仍然只有一套来源：

| 文档 | 用途 |
| --- | --- |
| `.agent/Research/README.md` | 产品入口和阅读顺序 |
| `.agent/Research/ARCHITECTURE.md` | 当前已批准的工程合同 |
| `.agent/Research/DDD.md` | 领域边界和模块连接 |
| `.agent/Research/CONVERSATION.md` | 对话节奏和表达合同 |
| `.agent/Research/DECISIONS.md` | 决策理由和取舍记录 |
| `REBUILD/README.md` | 重构过程、分支、阶段和交付门槛 |

新想法先作为提案讨论，不能直接成为系统规则。只有经过选择、写入对应文档并有验收方式，才进入实现。

## 6. 重构完成的判断

重构完成不是“代码全部重写”，而是下面几件事同时成立：

1. 用户场景有明确入口和结果；
2. 每个业务事实只有一个拥有者；
3. 模型、Core、调度、QQ和文件系统的边界清楚；
4. 失败、重试、取消和重启不会制造重复或虚假成功；
5. 关键行为有可重复的测试；
6. 生产数据可以备份、恢复和回滚；
7. 新版本可以独立运行，旧版本仍可回看；
8. 未验证的部分被明确标记，而不是用文档包装成完成。

这套方法的核心不是“重新写得更大”，而是让每一步都能被理解、验证、回退和继续。
